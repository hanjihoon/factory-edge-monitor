## 오늘 한 일
1. **Docker 빌드 실패 수정 (`3b6f6b8`)**
   - 증상: `docker compose up --build`에서 server 등 일부 이미지가 `Timeout waiting to lock journal cache`로 실패
   - 원인: 이미지 4개가 동시에 빌드되면서 여러 컨테이너의 Gradle이 같은 캐시 마운트(`/root/.gradle`)의 잠금을 두고 다툼. Gradle의 잠금 해제 요청이 컨테이너 경계를 넘지 못해 시간 초과
   - 수정: 캐시 마운트에 `sharing=locked` 지정 → 해당 빌드 단계를 순차 실행
   - 확인: 캐시를 비운 상태에서 `docker compose build --no-cache`로 이미지 5개 모두 빌드 성공
2. **전체 구성 실행 확인**: 컨테이너 8개 모두 기동. Flyway가 테이블 6개를 만들었고, 게이트웨이 2대가 연결해 데이터가 저장된다. 기동 직후의 게이트웨이 WARN은 서버가 뜨기 전 연결 재시도라 정상

**측정 스크립트 결함 2건 발견 → 수정 (`294b14c`)**
1. *해소 기준이 "미확인 0건"이었다.* 정상 상태에서도 전송 중·ack 대기 중인 수십~수백 건이 늘 있어서 0은 우연히만 찍힌다. 실제로는 2분 안에 해소됐는데 1분 넘게 더 기다려 185초가 나왔다. → "가장 오래된 미확인 레코드가 5초 미만"으로 변경
2. *복구 후 첫 보고 판정이 틀렸다.* `lastSeenAt`은 재연결만 해도 갱신되는데, 이때 서버의 적체 수치는 차단 직전 값(거의 0) 그대로다. 이번엔 우연히 92건이라 기다렸지만 0이었다면 복구 시간 0초로 나왔을 것이다. → 게이트웨이마다 "적체 보고 확인 → 해소" 두 단계를 거치도록 변경

참고: 이 측정의 지연 p50/p95(약 5~10분)는 차단 구간 데이터가 섞인 값이라 의미 없다. 지연은 정상 상태 측정값을 쓴다.

## 결정이 필요한 것: 복구 시간 목표 미달
"2분 안에 소진"은 과제가 준 수치가 아니라 직접 세운 가정이다. 선택지는 두 가지다.
1. **백오프 최대치를 30초에서 5~10초로 낮추고 다시 측정한다.** 재연결 대기가 줄어 목표 안에 들어올 가능성이 높다 (gw-a는 재연결 뒤 116초). 코드 한 줄을 고치고 측정에 15분이 든다. 대신 게이트웨이 수가 많을 때 서버에 재연결 시도가 더 자주 몰린다
2. **그대로 두고 "미달"로 기록한다.** 설계 문서에는 이미 미달과 원인을 적어 두었다
