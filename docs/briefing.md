### 1. 복구 시간 개선: 측정 → 원인 → 개선 → 재측정
모두 같은 조건(두 회선 600초 차단)에서 쟀고, 매번 유실 0건·중복 0건이었다.

| 단계 | 바꾼 것 | 적체 해소 | 화면 실시간 복귀 | 적체를 비우는 동안 새 데이터 지연 p95 |
|---|---|---|---|---|
| 기존 | 오래된 순 전송, 묶음 500 | 128초 | 130초 | 108초에서 점차 감소 |
| A | 묶음 2,000 (`727c30b`) | 78초 | 80초 | 67초에서 점차 감소 |
| C | + 실시간 우선 · 백필 · 범위 ack (`cc82b6d`) | 85초 | 100초 | 5~11초 |
| C' | + 전송 창 8 → 3 (`ef9e7e8`) | **79초** | **20초** | **1.1~3.3초** |

- **A: 묶음 크기를 키웠다.** 서버는 한 게이트웨이의 묶음을 하나씩 처리하고 묶음마다 고정 비용이 크다. 그래서 묶음을 4배로 키웠다
- **C: 새 데이터를 먼저 보낸다.** 적체를 빨리 비워도 새 데이터가 적체 뒤에 줄을 서면 화면은 과거를 보여 준다
  - 그래서 새 데이터를 먼저 보내고 밀린 데이터(백필)는 뒤에서 채운다
  - 보내는 순서가 섞이므로 ack를 "X번까지 전부"에서 "이 범위"로 바꿨다
- **C': 전송 창을 줄였다.** 백필 묶음 7개가 서버 앞에 줄을 서서 실시간 묶음이 기다렸다. 백필은 2개면 충분하다
- **B(백필 중 현재 상태 갱신 생략)는 하지 않았다.** 그대로 하면 현재 상태가 옛 값으로 남을 수 있어 안전하지 않다. 안전한 형태(seq가 클 때만 갱신)는 이미 들어 있다
- **백오프 단축(오전 선택지 1)도 하지 않았다.** 복구 시간의 주원인은 재연결 대기가 아니라 전송 속도였다

**측정 스크립트 결함 2건 발견 → 수정 (`294b14c`)**
1. *해소 기준이 "미확인 0건"이었다.* 정상 상태에서도 전송 중·ack 대기 중인 수십~수백 건이 늘 있어서 0은 우연히만 찍힌다. 실제로는 2분 안에 해소됐는데 1분 넘게 더 기다려 185초가 나왔다. → "가장 오래된 미확인 레코드가 5초 미만"으로 변경
2. *복구 후 첫 보고 판정이 틀렸다.* `lastSeenAt`은 재연결만 해도 갱신되는데, 이때 서버의 적체 수치는 차단 직전 값(거의 0) 그대로다. 이번엔 우연히 92건이라 기다렸지만 0이었다면 복구 시간 0초로 나왔을 것이다. → 게이트웨이마다 "적체 보고 확인 → 해소" 두 단계를 거치도록 변경

참고: 이 측정의 지연 p50/p95(약 5~10분)는 차단 구간 데이터가 섞인 값이라 의미 없다. 지연은 정상 상태 측정값을 쓴다.

## (오전) 결정이 필요했던 것: 복구 시간 목표 미달 → 오후에 해결
"2분 안에 소진"은 과제가 준 수치가 아니라 직접 세운 가정이다. 선택지는 두 가지다.
1. **백오프 최대치를 30초에서 5~10초로 낮추고 다시 측정한다.** 재연결 대기가 줄어 목표 안에 들어올 가능성이 높다 (gw-a는 재연결 뒤 116초). 코드 한 줄을 고치고 측정에 15분이 든다. 대신 게이트웨이 수가 많을 때 서버에 재연결 시도가 더 자주 몰린다
2. **그대로 두고 "미달"로 기록한다.** 설계 문서에는 이미 미달과 원인을 적어 두었다
