## 1. 30초 요약
- 설비 1,000대(공장 A MQTT 600, 공장 B Modbus 400)의 데이터를 폐쇄망 게이트웨이가 모아 중앙 서버로 보내고, 관제 화면에서 보고 정지·재개 명령을 내린다
- 핵심 약속은 하나다: **"게이트웨이 디스크에 들어온 데이터는 DB에 저장된 것이 확인되기 전에는 지우지 않는다."** 그래서 회선·서버·DB가 죽어도 유실이 없다
- 같은 데이터가 두 번 와도 서버가 `(설비 ID, seq)`로 한 번만 저장한다. 그래서 게이트웨이는 의심스러우면 그냥 다시 보내면 된다
- 장애 8종류를 실제 구성에서 일부러 일으켜 재 봤다 (아래 3장)

## 2. 데이터가 지나가는 길
```
설비 ──(MQTT/Modbus)──▶ 게이트웨이 ──(디스크 SQLite)──▶ 회선(WebSocket) ──▶ 서버 ──▶ TimescaleDB ──▶ 화면
                         ① 받으면 먼저 디스크에 기록       ② 묶음 전송          ③ 저장 커밋 뒤 ack   ④ ack 받은 범위만 디스크에서 삭제
```
- ① 디스크에 쓰기 전에는 설비(브로커)에게 "받았다"고 하지 않는다 (MQTT PUBACK을 커밋 뒤에)
- ③ 서버는 DB 커밋이 끝난 뒤에만 ack를 보낸다
- ④ 게이트웨이는 **자기가 보낸 묶음과 범위가 정확히 같은 ack**만 믿고 지운다

## 3. 장애별 대응 지도 (어디가 고장 → 누가 알아채고 → 어디서 무엇을 → 실측 결과)

| # | 고장 난 곳 | 무엇이 깨지나 | 누가 어떻게 알아채나 | 어디서 무엇을 하나 | 실측 결과 |
|---|---|---|---|---|---|
| 1 | **회선** (공장 ↔ 중앙) 10분 차단 | 데이터가 서버에 못 감 | 게이트웨이: 전송 실패 또는 ack 15초 무응답 → 연결 끊음. 화면: 게이트웨이 "끊김 (시각부터)" | **게이트웨이**: 계속 수집해 디스크에 쌓음. 재연결되면 새 데이터 먼저(실시간 줄), 밀린 것은 뒤에서(백필 줄). **서버**: 재전송 중복은 `(설비, seq)` 키로 버림 | 유실 0 · 중복 0 (6회), 적체 해소 66초, 화면 실시간 복귀 10초 |
| 2 | **서버** 강제 종료 30초 | 저장·ack가 멈춤 | 게이트웨이: 연결 끊김 | **게이트웨이**: 회선 단절과 똑같이 처리. **서버**: 커밋 전에 죽은 묶음은 ack가 안 나갔으므로 게이트웨이가 다시 보냄 | 유실 0 · 중복 0, 회복 33초 (Spring 기동 15초 포함) |
| 3 | **DB** 강제 종료 30초 | 저장 실패 | 서버: 저장 예외 | **서버**: ack 없이 게이트웨이 연결을 끊음 → 게이트웨이가 재전송. 실패한 트랜잭션은 중복 판정 기록까지 롤백되므로 재전송분이 "이미 봤다"로 버려지지 않음 | 유실 0 · 중복 0, 회복 18초 |
| 4 | **게이트웨이 A**(MQTT) 강제 종료 | 수집이 멈춤 | 서버: 연결 끊김 → 화면 "끊김" | **브로커**: 게이트웨이 몫을 대기열에 보관 (최대 36만 건 = 10분). **게이트웨이**: 다시 뜨면 디스크에 남은 것부터 전송, 브로커가 보관분을 넘겨줌 | 30초·200초 정지: 유실 0. 900초(허용 10분 초과): 18.7만 건 유실 = 설계대로 대기열 상한을 넘은 만큼 |
| 5 | **게이트웨이 B**(Modbus) 강제 종료 | 폴링이 멈춤 | 서버: 연결 끊김 | Modbus는 설비가 값을 보관하지 않음 → 꺼진 동안 샘플은 처음부터 수집되지 않음 (한계로 기록) | 30초에 약 13,000건 미수집 |
| 6 | **공장 브로커**(Mosquitto) 강제 종료 | 설비 → 게이트웨이 경로가 끊김 | 게이트웨이 상태 보고의 활성 설비 수가 0 | **설비(에뮬레이터)**: 끊긴 동안 발행분을 메모리 버퍼에 보관 후 재연결 시 전송. **브로커**: persistence 스냅숏에서 게이트웨이 구독을 되살려 게이트웨이가 붙기 전 메시지도 보관 (아래 5장의 발견) | persistence 끔 23,597건 유실 → 켬 1,726건 (남은 것은 종료 순간 메모리의 약 2초분). 게이트웨이 이후 구간은 0 |
| 7 | **같은 토큰으로 게이트웨이 2대** (설정 복제) | 두 대가 서로 밀어내며 재접속 반복 | 서버: 게이트웨이별 1분 접속 횟수 ≥ 5 → 화면에 "같은 토큰 중복 사용 의심", ERROR 로그 | 서버는 나중 연결을 남김. 운영자가 한쪽을 멈추되, 그쪽 적체가 0이 된 뒤에 멈춰야 함 | 60초 동안 71회 재접속, 경고 표시 확인 |
| 8 | **잘못된 데이터** (모르는 상태값, 남의 공장 설비, 30일보다 옛 시각) | 그대로 두면 묶음 전체가 저장 실패 → 무한 재전송 | 서버: 저장 전 검사 (`RecordCheck`) | **서버**: 그 레코드만 `ingest_rejected` 표로 격리, 나머지는 저장하고 ack | 단위·DB 테스트로 확인 |

**추가로: 명령 경로의 장애**
- 회선이 끊긴 동안 정지 명령 → 서버가 5초 × 3회 보내 보고 `TIMED_OUT`. 회선이 돌아와도 끝난 명령은 뒤늦게 실행되지 않음 (실측 확인)
- 같은 명령을 두 번 눌러도 commandId가 같아 한 번만 실행. 다른 내용으로 같은 ID 재사용 → 409
- 시간 초과 뒤 결과가 늦게 오면 "실패"가 아니라 "결과 모름"이었으므로 실제 결과로 바로잡고 감사 로그 `LATE_RESULT`

## 4. 오늘 추가한 것 (기대 이상을 노린 4가지)

### 4-1. 서버 병렬 저장 → 복구가 빨라짐
- **전에는:** 서버가 한 게이트웨이의 묶음을 하나씩 저장 → 게이트웨이당 초당 약 3,500건이 상한. 긴 단절 뒤 복구의 병목
- **바꾼 것:** 묶음을 작업 풀 4개에서 동시에 저장
- **왜 안전한가 (면접 핵심):** 정합성 규칙 셋이 모두 "순서와 무관"하게 설계돼 있었다
  1. ack는 "이 범위를 저장했다"(범위 ack) → 어떤 순서로 와도 맞는 범위만 지움
  2. 중복은 `(설비, seq)` 기본 키가 막음
  3. 현재 상태는 "seq가 더 클 때만" 갱신 → 늦게 끝난 옛 묶음이 최신 값을 덮지 않음
- **새로 생긴 위험과 대응:** 교착(deadlock). 묶음 1이 설비 A→B, 묶음 2가 B→A 순서로 행을 잠그면 서로 기다리며 멈춘다 → **모든 트랜잭션이 설비 ID 순서로 잠그게 정렬**. 같은 설비 200대를 다른 순서로 담은 묶음 8개 동시 저장 테스트로 확인
- **결과 (10분 단절, 같은 조건):** 적체 해소 79 → **66초**, 화면 실시간 복귀 20 → **10초**, 유실 0 · 중복 0
- **솔직한 평가:** 16% 개선으로 기대보다 작다. 창이 3이라 동시에 저장되는 백필이 2묶음뿐이고, 다음 병목은 게이트웨이 전송 스레드(SQLite 읽기 + JSON 직렬화를 하나씩)로 본다. 창 6 비교는 측정 PC 메모리 부족으로 중단

### 4-2. 속성 기반 테스트 (jqwik) → "유실 0"을 증명에 가깝게
- 사람이 떠올린 시나리오가 아니라, **사건 9종을 무작위로 섞은 시나리오 1,000개**를 자동 생성해 돌린다: 데이터 유입, 연결, 끊김, 전송, 서버 저장+ack, ack 유실, 저장 실패, ack 시간 초과, 게이트웨이 재시작
- 가짜 서버는 받은 묶음을 **아무 순서로나** 처리한다 (병렬 저장과 같음)
- 매 사건 뒤 확인: "디스크에서 지운 레코드는 반드시 DB에 있다"
- **테스트가 진짜 버그를 잡는지 확인:** ack 처리를 일부러 틀리게(누적 ack처럼 앞쪽까지 지우게) 바꾸자 실패했고, jqwik이 재현 시나리오를 5단계로 줄여 보여 줬다: 데이터 → 연결 → 데이터 → 전송 → 저장+ack

### 4-3. 가동률 KPI (선택 구현)
- 가동률 = 가동 상태로 보고된 초 ÷ 보고된 초. 생산 수량·불량 데이터가 없어서 OEE의 성능·품질은 계산하지 않는다
- TimescaleDB **연속 집계**가 1분마다 미리 세어 둠 → 24시간 조회가 원본 8,640만 행 대신 144만 행
- 회선이 끊겨 6시간 늦게 온 데이터도 반영되도록 갱신 범위를 7시간으로 잡음
- 화면: 공장별 가동률, 시간대별 막대, 가동률 낮은 설비 5대 (클릭 → 설비 상세)

### 4-4. 지연 예산 (어디서 시간이 드나)
측정 → DB 지연을 두 구간으로 나눴다 (`scripts/report.sql` 2-1번)

| 구간 | 공장 A (MQTT) p50 / p95 | 공장 B (Modbus) p50 / p95 |
|---|---|---|
| 설비 → 게이트웨이 | 184ms / 1.6초 | 0 (폴링 시각 = 측정 시각) |
| 게이트웨이 → DB (우리 파이프라인) | 28ms / 81ms | 172ms / 836ms |

- **결론 1:** 공장 A 지연의 대부분은 설비 → 게이트웨이 구간이다. 에뮬레이터가 일부러 넣는 0~300ms 지연과 브로커 수신이다. 우리가 만든 게이트웨이 → DB는 p95 0.1초 미만
- **결론 2:** 약 7초마다 두 공장이 동시에 0.5~1.6초 튄다. DB 커밋(p95 8ms)·서버 GC(최대 20ms)·게이트웨이(동시에 튐)는 배제했고 원인은 못 찾았다 (같은 PC를 나눠 쓰는 호스트 스케줄링 의심)
- **결론 3:** 공장 B가 A보다 느린 것은 폴링이 0.5초마다 400대를 몰아서 읽어 데이터가 뭉쳐 오기 때문으로 본다 (A 설비는 1초 안에 고르게 흩어져 발행)

## 5. 오늘 스스로 찾은 잘못 (면접에서 솔직하게)
- **브로커 손실의 원인을 잘못 짚었다.** 처음엔 "브로커가 죽은 동안 설비 발행이 실패해서"라고 썼다. 로그를 다시 보니:
  1. 설비는 끊긴 동안 발행분을 버퍼에 보관했다가 재연결 즉시 몰아서 보냈다
  2. 그런데 브로커가 `persistence false`라 재시작하면서 **게이트웨이의 구독 정보가 사라졌다**
  3. 게이트웨이가 다시 구독하기까지 7~17초 동안 도착한 메시지는 **받을 사람이 없어 버려졌다**
- 같은 현상을 설정 변경용 일반 재시작에서도 확인 (2만 807건). 즉 **정전이 아니라 브로커를 재시작하기만 해도** 유실이 났다 → persistence를 켜는 쪽으로 판단을 바꿈
- **측정 스크립트가 너무 일찍 집계했다.** 브로커 대기열이 아직 전달 중일 때 집계해 유실을 못 봤다 → "저장 건수가 멈출 때까지 기다린 뒤 집계"로 고침

## 6. 예상 질문
| 질문 | 답의 요지 |
|---|---|
| 정확히 한 번 전달인가? | 아니다. **최소 한 번 전달 + 서버 중복 제거**로 결과가 정확히 한 번과 같다. 진짜 정확히 한 번은 분산 환경에서 비싸고, 키 하나로 충분했다 |
| 왜 누적 ack가 아니라 범위 ack? | 새 데이터를 먼저 보내므로 순서가 섞인다. 누적 ack면 새 묶음의 ack로 아직 안 보낸 옛 묶음까지 지워진다 → 유실. 속성 테스트가 이것을 5단계로 재현한다 |
| 왜 Redis로 중복 판정 안 했나? | 판정과 저장이 한 트랜잭션이어야 한다. Redis에 "봤다"를 남기고 DB 저장이 실패하면 재전송분이 중복으로 버려진다 |
| 병렬 저장하면 순서가 꼬이지 않나? | 4-1의 규칙 셋. 교착은 잠금 순서 정렬로 |
| 6시간 넘게 끊기면? | 디스크 버퍼 상한을 넘으면 가장 오래된 것부터 버리고 유실 건수를 화면에 올린다. 다음 단계는 버리는 대신 다운샘플링 |
| 정전이면? | 게이트웨이 디스크는 커밋마다 디스크에 강제 기록(`synchronous=FULL`)이라 남는다(설정 근거, 실제 전원 차단 시험은 못 함). 브로커 메모리의 방금 받은 메시지는 사라질 수 있어 UPS를 배치 요구사항으로 둠 |
