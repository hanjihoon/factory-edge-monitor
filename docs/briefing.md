## 1. 30초 요약
- 공장 2곳의 설비 1,000대(공장 A: MQTT 600대, 공장 B: Modbus 400대)가 1초마다 상태를 보고한다
- 공장마다 있는 **게이트웨이**가 이것을 모아 중앙 **서버**로 보내고, 서버는 DB에 저장하고 **관제 화면**에 보여 준다. 운영자는 화면에서 설비를 정지·재개할 수 있다
- 공장망은 폐쇄망이라 **게이트웨이가 먼저 밖으로 연결**해야 하고, 회선은 수시로 끊긴다
- 핵심 약속은 하나다: **"게이트웨이 디스크에 들어온 데이터는, DB에 저장됐다는 확인(ack)을 받기 전에는 지우지 않는다."** 그래서 회선·서버·DB가 죽어도 유실이 없다
- 같은 데이터가 두 번 와도 서버가 `(설비 ID, seq)`로 한 번만 저장한다. 그래서 게이트웨이는 의심스러우면 그냥 다시 보내면 된다
- 장애 8종류를 실제 구성에서 일부러 일으켜 쟀다 (4장)

## 2. 용어 풀이 (이것만 알면 나머지가 읽힌다)

| 용어 | 쉬운 설명 | 이 프로젝트에서 |
|---|---|---|
| **seq** | 설비가 보고할 때마다 1씩 올리는 번호 | `(설비 ID, seq)`가 같으면 같은 데이터다. 중복 판정과 순서 판정의 유일한 기준 |
| **outbox (디스크 버퍼)** | 보낼 편지를 넣어 두는 우편함. 상대가 받았다고 답해야 꺼낸다 | 게이트웨이의 SQLite 파일. 회선이 끊기면 여기에 쌓인다 (최대 6시간분) |
| **ack** | "받았다(저장했다)"는 답장 | 서버가 **DB 커밋이 끝난 뒤에만** 보낸다. 게이트웨이는 ack를 받은 것만 outbox에서 지운다 |
| **범위 ack** | "1001번~3000번 묶음을 저장했다"처럼 범위로 답함 | 반대는 "3000번까지 전부 받았다"(누적 ack). 우리는 순서를 섞어 보내므로 누적 ack를 쓰면 유실이 난다 (6장 질문) |
| **최소 한 번 전달** | 잃어버리지 않는 대신 두 번 갈 수는 있음 | 게이트웨이는 확실하지 않으면 다시 보낸다 → 서버가 중복을 버린다 → 결과는 "정확히 한 번"과 같다 |
| **멱등** | 같은 요청을 여러 번 해도 결과가 한 번 한 것과 같음 | 명령마다 `commandId`. 같은 ID로 다시 와도 설비에는 한 번만 적용 |
| **실시간 줄 / 백필 줄** | 회선 복구 직후 "새 데이터"와 "끊긴 동안 밀린 데이터"를 나눠 보내는 두 줄 | 새 데이터를 먼저 보내 화면이 빨리 현재로 돌아온다. 밀린 것은 남는 자리로 채운다 |
| **창 (window)** | ack를 기다리지 않고 미리 보내 둘 수 있는 묶음 수 | 3 (실시간 1 + 백필 2). 묶음 하나는 최대 2,000건 |
| **QoS 1 / PUBACK** | MQTT에서 "최소 한 번 전달" 모드와 그 확인 응답 | 게이트웨이는 디스크에 기록한 **뒤에** 브로커에 PUBACK. 그 전에 죽으면 브로커가 다시 준다 |
| **브로커 (Mosquitto)** | 공장 A 안의 MQTT 우체국. 설비가 보낸 메시지를 게이트웨이에 전달 | 게이트웨이가 잠시 꺼져도 최대 10분(36만 건)까지 대신 보관 |
| **persistence** | 브로커가 자기 상태를 디스크에 저장해 두는 설정 | 켜야 브로커 재시작 뒤에도 게이트웨이의 구독이 남는다 (5장의 발견) |
| **hypertable / 연속 집계** | TimescaleDB의 시간 분할 테이블 / 미리 계산해 두는 집계 | 원본은 1일 단위로 나뉘고 2일 지나면 압축(8배). 가동률은 1분 단위로 미리 센다 |
| **교착 (deadlock)** | 두 작업이 서로 상대가 쥔 잠금을 기다리며 영원히 멈춤 | 병렬 저장에서 생길 수 있어 잠그는 순서를 설비 ID 순으로 맞췄다 |
| **toxiproxy** | 회선 장애를 흉내 내는 중계 프로그램 | 게이트웨이 ↔ 서버 사이에 있다. 끊기, 지연 주기 |

## 3. 시간 순서로 보는 세 가지 흐름

### 3-1. 정상일 때 데이터 하나가 화면에 뜨기까지 (평균 약 0.26초)
1. **설비 → 게이트웨이.** 공장 A 설비는 브로커에 MQTT로 발행하고 게이트웨이가 구독해 받는다. 공장 B는 게이트웨이가 0.5초마다 Modbus 레지스터를 읽는다
2. **정규화.** 두 프로토콜을 같은 모양(`TelemetryRecord`: 설비 ID, seq, 측정 시각, 상태, 온도, 진동, 회전수, 알람)으로 바꾼다
3. **디스크 기록.** outbox(SQLite)에 모아서 한 번에 기록한다. 기록이 끝나야 브로커에 PUBACK을 보낸다 → **이 순간부터 유실이 없다**
4. **전송.** 전송 스레드가 outbox에서 최대 2,000건을 꺼내 묶음(BATCH)으로 WebSocket에 보낸다
5. **서버 저장.** 서버는 한 SQL 문으로 "중복 판정표에 넣기 → 처음 보는 것만 시계열 테이블에 넣기 → 설비 현재 상태 갱신(seq가 클 때만)"을 하고 커밋한다
6. **ack.** 커밋이 끝나면 받은 묶음의 범위를 그대로 ack로 돌려준다. 게이트웨이는 그 범위만 outbox에서 지운다
7. **화면.** 서버는 바뀐 설비만 0.25초마다 모아 화면 WebSocket으로 보낸다

### 3-2. 회선이 10분 끊겼다가 돌아올 때
1. 끊기는 순간: 게이트웨이의 전송이 실패하거나, 보낸 묶음의 ack가 15초 안에 안 오면 "끊겼다"고 판단하고 연결을 닫는다
2. 끊긴 동안: 수집은 그대로 계속되고 outbox에 쌓인다 (공장 A 약 36만 건). 게이트웨이는 0.5초 → 1초 → 2초 … 최대 30초 간격으로 재연결을 시도한다
3. 화면: 게이트웨이 표가 빨간 "끊김 (18시 48분 37초부터)", 적체는 "알 수 없음 · 끊기기 전 93건". 끊긴 동안 서버는 진짜 적체를 모르므로 숫자를 지어내지 않는다
4. 돌아오는 순간: 재연결되면 그때 outbox의 마지막 번호를 경계로 **이전 것은 백필 줄, 이후 것은 실시간 줄**로 나눈다
5. 실시간 줄을 항상 먼저 보낸다 → **10초 만에 화면이 현재로 돌아온다.** 백필은 남는 자리 2개로 계속 보낸다 → **66초 만에 적체가 다 빠진다**
6. 끊기기 직전에 보냈지만 ack를 못 받은 묶음은 outbox에 남아 있어 다시 간다. 서버가 이미 저장했다면 중복 판정표가 버린다
7. 결과: 6회 측정 모두 유실 0, 중복 0

### 3-3. 운영자가 정지 버튼을 누를 때
1. 화면이 `commandId`(무작위 ID)를 만들어 서버에 요청한다. 더블클릭이나 응답 지연으로 다시 눌러도 같은 ID라 명령은 하나만 생긴다
2. 서버는 조회자면 403으로 거부하고, 운영자면 명령을 저장하고 감사 로그 `REQUESTED`
3. 서버가 **게이트웨이가 열어 둔 WebSocket을 거꾸로 이용해** 명령을 내려보낸다 (공장망은 들어오는 연결을 받지 않으므로)
4. 게이트웨이가 설비에 전달한다 (MQTT 명령 토픽 / Modbus 제어 레지스터 쓰기). 설비가 결과를 돌려준다
5. 5초 안에 결과가 없으면 서버가 같은 commandId로 다시 보낸다 (최대 3회). 게이트웨이와 설비는 같은 ID를 다시 실행하지 않는다
6. 3회 모두 응답이 없으면 `TIMED_OUT`. 이것은 "실패"가 아니라 "결과 모름"이라, 나중에 진짜 결과가 오면 그것으로 바로잡는다 (`LATE_RESULT`)
7. 실측: 안정 상태 왕복 약 0.4초, 확인 항목 21개 통과

## 4. 장애별 대응 지도
읽는 법: **어디가 고장 → 무엇이 깨지나 → 누가 알아채나 → 어디서 무엇을 하나 → 실측 결과**

| # | 고장 난 곳 | 무엇이 깨지나 | 누가 어떻게 알아채나 | 어디서 무엇을 하나 | 실측 결과 |
|---|---|---|---|---|---|
| 1 | **회선** (공장 ↔ 중앙) 10분 차단 | 데이터가 서버에 못 감 | 게이트웨이: 전송 실패 또는 ack 15초 무응답. 화면: "끊김 (시각부터)" | **게이트웨이**: 계속 수집해 디스크에 쌓음. 재연결되면 실시간 줄 먼저, 백필 줄은 뒤에서. **서버**: 재전송 중복은 `(설비, seq)` 키로 버림 | 유실 0 · 중복 0 (6회), 적체 해소 66초, 화면 실시간 복귀 10초 |
| 2 | **서버** 강제 종료 30초 | 저장·ack가 멈춤 | 게이트웨이: 연결 끊김 | **게이트웨이**: 회선 단절과 똑같이 처리. **서버**: 커밋 전에 죽은 묶음은 ack가 안 나갔으므로 게이트웨이가 다시 보냄 | 유실 0 · 중복 0, 회복 33초 (Spring 기동 15초 포함) |
| 3 | **DB** 강제 종료 30초 | 저장 실패 | 서버: 저장 예외 | **서버**: ack 없이 게이트웨이 연결을 끊음 → 게이트웨이가 재전송. 실패한 트랜잭션은 중복 판정 기록까지 되돌리므로 재전송분이 "이미 봤다"로 버려지지 않음 | 유실 0 · 중복 0, 회복 18초 |
| 4 | **게이트웨이 A**(MQTT) 강제 종료 | 수집이 멈춤 | 서버: 연결 끊김 → 화면 "끊김" | **브로커**: 게이트웨이 몫을 대기열에 보관 (최대 36만 건 = 10분). **게이트웨이**: 다시 뜨면 디스크에 남은 것부터 전송, 브로커가 보관분을 넘겨줌 | 30초·200초: 유실 0. 900초(허용 10분 초과): 187,108건 유실 = 대기열 상한을 넘은 만큼, 설계대로 |
| 5 | **게이트웨이 B**(Modbus) 강제 종료 | 폴링이 멈춤 | 서버: 연결 끊김 | 방법 없음: Modbus 설비는 지난 값을 보관하지 않아 꺼진 동안 샘플은 처음부터 수집되지 않음 (한계로 기록) | 30초에 약 13,000건 미수집 |
| 6 | **공장 브로커** 강제 종료 30초 | 설비 → 게이트웨이 경로가 끊김 | 게이트웨이 상태 보고의 활성 설비 수가 0 | **설비**: 끊긴 동안 발행분을 버퍼에 보관 후 재연결 시 전송. **브로커**: persistence 스냅숏에서 게이트웨이 구독을 되살려 게이트웨이가 붙기 전 메시지도 보관 | persistence 끔 23,597건 → 켬 **1,726건** (남은 것은 종료 순간 브로커 메모리에만 있던 약 2초분). 게이트웨이 이후 구간은 0 |
| 7 | **같은 토큰으로 게이트웨이 2대** (설정 복제) | 두 대가 서로 밀어내며 재접속 반복, 데이터가 두 디스크로 나뉨 | 서버: 게이트웨이별 1분 접속 횟수 ≥ 5 → 화면 "같은 토큰 중복 사용 의심", ERROR 로그 | 서버는 나중 연결을 남김. 운영자가 한쪽을 멈추되, **그쪽 적체가 0이 된 뒤에** 멈춰야 함 (안 그러면 그 디스크의 미전송분 유실) | 60초에 71회 재접속, 경고 표시 확인 |
| 8 | **잘못된 데이터** (모르는 상태값, 남의 공장 설비, 30일보다 옛 시각) | 그대로 두면 묶음 전체가 저장 실패 → 무한 재전송 → 그 게이트웨이 전체가 멈춤 | 서버: 저장 전 검사 (`RecordCheck`) | **서버**: 그 레코드만 `ingest_rejected` 표로 격리, 나머지는 저장하고 ack | 단위 테스트, 실제 DB 테스트 |

**명령 경로의 장애**
- 회선이 끊긴 동안 정지 명령 → 서버가 5초 × 3회 보내 보고 `TIMED_OUT`. 회선이 돌아와도 끝난 명령은 뒤늦게 실행되지 않음 (실측)
- 같은 명령을 두 번 눌러도 commandId가 같아 한 번만 실행. 다른 내용으로 같은 ID를 쓰면 409
- 게이트웨이 재시작 직후에는 왕복이 9.5초(재시도 3회)까지 늘었다: 설비의 명령 응답이 밀려 들어오는 텔레메트리와 같은 MQTT 수신 대기열에 줄을 섰기 때문. 결과는 멱등이라 정상. 한계로 기록 (응답 전용 연결이 다음 단계)

## 5. 오늘 추가한 것 (기대 이상을 노린 4가지)

### 5-1. 서버 병렬 저장 → 복구가 빨라짐 (`GatewayWebSocketHandler`, `LatestPerDevice`)
- **전에는:** 서버가 한 게이트웨이의 묶음을 하나씩 저장 → 복구 중 게이트웨이당 초당 약 4,600건이 상한
- **바꾼 것:** 묶음(BATCH)을 작업 풀(스레드 4개)에 넘기고 수신 스레드는 바로 다음 메시지를 읽는다
- **왜 안전한가 (면접 핵심):** 정합성 규칙 셋이 처음부터 "순서와 무관"하게 설계돼 있었다
  1. ack는 범위 ack → 어떤 순서로 와도 보낸 범위와 정확히 같은 것만 지움
  2. 중복은 `(설비, seq)` 기본 키가 막음
  3. 현재 상태는 "seq가 더 클 때만" 갱신 → 늦게 끝난 옛 묶음이 최신 값을 덮지 않음
- **새로 생긴 위험과 대응:** 교착. 묶음 1이 설비 A→B, 묶음 2가 B→A 순서로 현재 상태 행을 잠그면 서로 기다리며 멈춘다 → **모든 트랜잭션이 설비 ID 순서로 잠그게 정렬** (`LatestPerDevice`가 `TreeMap` 사용, 중복 판정 SQL에 `ORDER BY device_id, seq`). 같은 설비 200대를 다른 순서로 담은 묶음 8개 동시 저장 테스트로 확인
- **결과 (10분 단절, 같은 조건):** 적체 해소 79 → **66초**, 화면 실시간 복귀 20 → **10초**, 유실 0 · 중복 0
- **솔직한 평가:** 16% 개선으로 기대보다 작다. 창이 3이라 동시에 저장되는 백필이 2묶음뿐이고, 다음 병목은 게이트웨이 전송 스레드 하나가 SQLite 읽기 + JSON 변환을 순서대로 하는 것으로 본다. 창 6 비교 측정은 PC 메모리 부족으로 중단

### 5-2. 속성 기반 테스트 → "유실 0"을 증명에 가깝게 (`UplinkPropertyTest`)
- 사람이 떠올린 시나리오가 아니라, **사건 9종을 무작위로 섞은 시나리오 1,000개**를 jqwik이 자동으로 만든다: 데이터 유입, 연결, 끊김, 전송, 서버 저장+ack, ack 유실, 저장 실패, ack 시간 초과, 게이트웨이 재시작
- 진짜 게이트웨이 코드(`Uplink` + SQLite outbox)에 가짜 서버를 붙인다. 가짜 서버는 받은 묶음을 **아무 순서로나** 처리한다 (병렬 저장과 같음)
- 매 사건 뒤 확인: **"디스크에서 지운 레코드는 반드시 DB에 있다."** 마지막에 회선을 정상으로 두면 전부 DB에 있어야 한다
- **테스트가 진짜 버그를 잡는지 확인:** ack 처리를 일부러 틀리게(누적 ack처럼 앞쪽까지 지우게) 바꾸자 실패했고, jqwik이 재현 시나리오를 **5단계**로 줄여 보여 줬다: 데이터 → 연결 → 데이터 → 전송 → 저장+ack

### 5-3. 가동률 KPI (`V5__kpi_availability.sql`, `KpiService`, `KpiPanel.tsx`)
- 가동률 = 가동 상태로 보고된 초 ÷ 보고된 초. 생산 수량·불량 데이터가 없어서 OEE의 성능·품질은 계산하지 않는다 (없는 데이터로 숫자를 만들지 않음)
- TimescaleDB **연속 집계**가 1분마다 설비별 상태 개수를 미리 센다 → 24시간 조회가 원본 8,640만 행 대신 144만 행
- 회선이 끊겨 최대 6시간 늦게 온 데이터도 반영되도록 다시 세는 범위를 7시간으로 잡음
- 화면: 1시간·24시간·7일 선택, 공장별 가동률, 시간대별 막대, 가동률 낮은 설비 5대 (클릭 → 설비 상세)

### 5-4. 지연 구간 분석 (`scripts/report.sql` 2-1번)
| 구간 | 공장 A (MQTT) p50 / p95 | 공장 B (Modbus) p50 / p95 |
|---|---|---|
| 설비 → 게이트웨이 | 184ms / 1.6초 | 0 (폴링 시각 = 측정 시각) |
| 게이트웨이 → DB (우리 파이프라인) | 28ms / 81ms | 172ms / 836ms |
| 측정 → 화면 (전체) | p50 약 0.26초, p95는 13회 중 11회 2초 안, 2회 2.5~2.6초 | (화면은 공장 구분 없이 측정) |

- 공장 A 지연의 대부분은 설비 → 게이트웨이 구간이다. 에뮬레이터가 일부러 넣는 0~300ms 지연과 브로커 수신이다. 우리가 만든 게이트웨이 → DB는 p95 0.1초 미만
- 공장 B가 A보다 느린 것은 폴링이 0.5초마다 400대를 몰아서 읽어 데이터가 뭉쳐 오기 때문으로 본다 (A 설비는 1초 안에 고르게 흩어져 발행)
- 화면 p95가 2초를 넘은 2회는 7장의 일시적 지연과 겹친다

## 6. 스스로 찾은 잘못 (면접에서 솔직하게)
- **브로커 손실의 원인을 잘못 짚었다.** 처음엔 "브로커가 죽은 동안 설비 발행이 실패해서"라고 썼다. 로그를 다시 보니:
  1. 설비는 끊긴 동안 발행분을 버퍼에 보관했다가 재연결 즉시 몰아서 보냈다
  2. 그런데 브로커 persistence가 꺼져 있어 재시작하면서 **게이트웨이의 구독 정보가 사라졌다**
  3. 게이트웨이가 다시 구독하기까지 7~17초 동안 도착한 메시지는 **받을 사람이 없어 버려졌다**
  - 설정 변경용 일반 재시작에서도 20,807건. 즉 정전이 아니라 **브로커를 재시작하기만 해도** 유실이 났다 → persistence를 켜는 쪽으로 판단을 바꿈
- **측정 스크립트가 너무 일찍 집계했다.** 브로커 대기열이 아직 전달 중일 때 집계해 게이트웨이 200초 정지의 유실(25,592건)을 못 봤다 → "저장 건수가 멈출 때까지 기다린 뒤 집계"로 고침
- **화면이 실제 브라우저에서 연결되지 않던 문제.** nginx가 서버로 넘기는 Host 값에서 포트를 빼먹어 서버의 같은 출처 검사가 브라우저 연결을 403으로 막았다. curl로만 확인해서 몰랐다 → 고치고 확인 스크립트에 브라우저와 같은 조건의 검사(0번)를 넣음

### 7-1. 일시적 지연 원인을 찾은 과정 (면접에서 "어떻게 찾았나" 질문용)
1. **현상:** 정상 상태인데 7~40초마다 1~2초 동안 저장 지연이 0.5~2초로 튄다. 두 공장이 같은 순간에
2. **같은 순간이라는 점에서 공통 부품을 의심:** 서버, DB, 회선 흉내 프로그램, PC 전체
3. **하나씩 배제:** DB 커밋은 최대 29ms. 서버 GC는 최대 20ms. 그 순간에도 서버 HTTP·DB가 바로 응답 → PC 전체 멈춤 아님. 공장 B를 회선 흉내 프로그램 없이 서버에 바로 붙여도 같이 튐 → 회선 프로그램 아님
4. **실행 기록(JFR)을 서버·게이트웨이 둘에 동시에 켬:** GC는 최대 25ms로 무관. 그런데 두 게이트웨이 모두 디스크 버퍼에 쓰는 스레드가 잠금을 **최대 1.6초** 쥐고 있었고, 서버 ack를 처리하는 스레드가 그 잠금을 기다렸다
5. **디스크 자체를 따로 잼:** 상관없는 컨테이너에서 0.2초마다 작은 동기 쓰기를 150초. 0.15~0.53초 멈춤 27번, 저장 지연이 튄 시각과 거의 일치
6. **결론:** 모든 컨테이너가 나눠 쓰는 측정 PC의 가상 디스크가 가끔 멈춘다. 게이트웨이는 정전에도 안전하려고 기록마다 디스크 확인을 기다리므로(`synchronous=FULL`) 그 멈춤이 그대로 지연이 된다. 실제 공장은 장비가 따로라 두 공장이 동시에 멈추지 않는다
7. **고치지 않은 이유:** 디스크 확인을 생략(`synchronous=NORMAL`)하면 지연은 줄지만 정전 때 마지막 몇 건을 잃을 수 있다. "유실 0"이 더 중요한 약속이라 지연 쪽을 한계로 기록했다

## 8. 예상 질문
| 질문 | 답의 요지 |
|---|---|
| 정확히 한 번 전달인가? | 아니다. **최소 한 번 전달 + 서버 중복 제거**로 결과가 정확히 한 번과 같다. 진짜 정확히 한 번은 분산 환경에서 비싸고, 키 하나로 충분했다 |
| 왜 누적 ack가 아니라 범위 ack? | 새 데이터를 먼저 보내므로 순서가 섞인다. 누적 ack면 새 묶음의 ack("3000번까지 받음")로 아직 안 보낸 옛 묶음(1000번대)까지 지워진다 → 유실. 속성 테스트가 이것을 5단계로 재현한다 |
| 왜 Redis로 중복 판정 안 했나? | 판정과 저장이 한 트랜잭션이어야 한다. Redis에 "봤다"를 남기고 DB 저장이 실패하면 재전송분이 중복으로 버려진다 |
| 병렬 저장하면 순서가 꼬이지 않나? | 5-1의 규칙 셋. 교착은 잠금 순서 정렬로 |
| 왜 게이트웨이가 서버로 연결하나? | 공장망은 밖에서 들어오는 연결을 받지 않는다. 게이트웨이가 연 연결 하나로 데이터는 올리고 명령은 내려받는다 |
| 6시간 넘게 끊기면? | 디스크 버퍼 상한을 넘으면 가장 오래된 것부터 버리고 유실 건수를 화면에 올린다. 다음 단계는 버리는 대신 다운샘플링 |
| 정전이면? | 게이트웨이 디스크는 커밋마다 디스크에 강제 기록(`synchronous=FULL`)이라 남는다 (설정 근거, 실제 전원 차단 시험은 못 함). 브로커 메모리의 방금 받은 메시지는 사라질 수 있어 UPS를 배치 요구사항으로 둠 |
| 공장이 100곳이 되면? | 가장 먼저 중복 판정표(이틀에 1,700억 행)가 터진다. seq가 설비마다 늘어나기만 한다는 점을 이용해 "설비별 최고 seq + 최근 범위 비트맵"으로 바꾸면 행 수가 아니라 설비 수에 비례한다 (설계 문서 12장) |
