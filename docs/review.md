### 1번 자세히: "독이 든 메시지" 문제
- 서버는 저장에 실패하면 ack 없이 연결을 끊고, 게이트웨이는 같은 묶음을 다시 보낸다. DB가 잠깐 죽은 경우라면 이게 맞는 동작이다.
- 그런데 **데이터 자체가 잘못된 경우**(예: 필드가 비어 있음, 게이트웨이를 새 버전으로 올려 서버가 모르는 상태 값 `MAINTENANCE`를 보냄)는 몇 번을 다시 보내도 실패한다.
  - 그러면 "실패 → 끊기 → 재연결 → 같은 묶음 → 실패"가 끝없이 반복된다
  - 그 게이트웨이의 **다른 정상 데이터도 전부 막힌다**
  - 6시간이 지나면 버퍼 상한으로 버려진다
- 고치는 방향은 **격리(dead letter)** 다. 잘못된 레코드는 원문 그대로 별도 테이블에 보관하고, 나머지는 저장하고, 묶음은 ack한다.
  - 버리지 않으니 유실이 아니다
  - 무한 재시도도 없다
  - 운영자가 나중에 원인을 볼 수 있다

## 2. Redis 도입 검토

결론: **지금 구조(서버 1대)에는 넣지 않는다. 서버를 여러 대로 늘릴 때 "공유 상태" 용도로 넣는다. 데이터 정합성의 핵심 경로(중복 판정·ack)에는 넣지 않는다.**

### 후보별 판단
| 후보 | 얻는 것 | 잃는 것 / 위험 | 판단 |
|---|---|---|---|
| **중복 판정을 Redis로** (`SET key NX EX 6h`) | 가장 큰 테이블(이틀에 17GB)과 묶음마다 하는 쓰기 한 번이 사라진다 | Redis 판정과 DB 커밋이 한 트랜잭션이 아니다. 아래 "유실 시나리오" 참고. **유실 0 보장을 깨뜨린다** | **넣지 않는다** |
| 로그인 세션 저장 | 서버 재시작·여러 대에서도 로그인 유지, 만료(TTL) 자동 | 서버 1대인 지금은 이득이 없다 | 다중 서버 때 |
| 게이트웨이 상태(연결·적체) 공유 | 여러 서버가 같은 화면 정보를 본다 | 〃 | 다중 서버 때 |
| **명령 라우팅** (게이트웨이가 붙은 서버로 명령 전달) | 게이트웨이 WebSocket은 서버 한 대에만 붙는다. 다른 서버가 받은 명령을 그 서버로 넘겨야 한다 → Pub/Sub | 메시지가 사라질 수 있음 (Pub/Sub는 저장하지 않음). 명령 재시도(5초×3회)가 이미 있어 감당 가능 | 다중 서버 때 핵심 |
| 화면 실시간 전송 분배 | 서버 A가 저장한 변경을 서버 B에 붙은 브라우저에도 → Pub/Sub | 〃 | 다중 서버 때 |
| 명령 잠금 | 지금은 서버 메모리의 잠금 하나 → 여러 대면 무효 | 분산 잠금은 미묘하다 (잠금 만료 중 GC 정지 등) | **Redis 대신 DB 행 잠금**(`SELECT … FOR UPDATE`)이 단순하고 정확하다 |
| 설비 현재 상태 캐시 | 화면 첫 로딩을 빠르게 | 1,000행이라 DB에서 읽어도 수 ms. 캐시 무효화 부담만 생긴다 | 필요 없음 |
| 수신 큐 (Redis Streams) | 서버가 받자마자 큐에 넣고 여러 작업자가 병렬 저장 → "게이트웨이당 직렬 처리" 병목 해소 | ack를 큐 적재 뒤에 보내면 Redis 장애 시 유실. DB 커밋 뒤에 보내려면 결국 지금과 같은 구조 | 규모가 커지면 Kafka 쪽이 맞다 |

### 중복 판정을 Redis로 옮기면 생기는 유실 시나리오
1. 묶음이 들어온다 → Redis `SET NX` 성공 ("처음 보는 데이터")
2. DB 저장 중 오류 → 롤백 → ack 안 보냄 (지금 설계대로)
3. 게이트웨이가 같은 묶음을 다시 보낸다 → Redis는 "이미 봤다"고 판단 → 저장하지 않고 ack
4. 게이트웨이는 ack를 받고 지운다 → **DB에도 없고 게이트웨이에도 없다 = 유실**

이 순서를 맞추려면 "DB 커밋 뒤에 Redis 기록 + 그 사이 장애 시 보정"이 필요하다. 결국 DB 유니크 키가 최종 판정을 해야 한다. 그러면 Redis는 앞단 필터일 뿐이라 얻는 게 적다.
**지금 설계가 중복 판정을 DB 유니크 키 하나에 맡긴 이유가 바로 이것이다.** 저장과 판정이 같은 트랜잭션 안에 있어야 한다.

### 그래도 커지는 중복 판정표는 어떻게 하나 (Redis 없이)
- 날짜별 테이블로 나눠, 이틀 지난 테이블은 `DROP` 한다. 행 단위 `DELETE`가 없어진다.
  - 판정은 "오늘 + 어제" 두 테이블을 본다
  - 재전송은 버퍼 상한(6시간) 안에서만 생기므로 충분하다
- 또는 시계열 테이블의 기본 키 `(device_id, device_ts, seq)`로 판정한다.
  - 재전송된 레코드는 측정 시각까지 똑같기 때문이다
  - 남는 예외는 "게이트웨이 재시작 뒤 Modbus가 같은 seq를 다른 폴링 시각으로 다시 읽는 경우" 하나다. 이 경우만 게이트웨이가 디스크에 마지막 seq를 남겨 막으면 된다

## 3. 과제 범위 밖이지만 하면 좋은 것

"과제를 끝냈다"를 넘어 **"현장에서 돌아갈 시스템을 생각했다"** 를 보여 줄 수 있는 항목이다. 비용은 대략의 작업 시간이다.

### A. 신뢰성을 실측으로 증명하기 (지금 강점의 연장)
| 항목 | 왜 의미 있나 | 비용 |
|---|---|---|
| **반쯤 죽은 회선 시험** (지연 10초, 대역폭 제한, 패킷 끊김) | 지금은 "완전히 끊김"만 실측했다. 실제 공장 회선은 느려지거나 간헐적으로 끊기는 경우가 더 흔하다. ack 15초 시간 초과 경로를 실제로 검증한다. toxiproxy에 latency·bandwidth·timeout 옵션이 이미 있다 | 1h |
| **다른 장애도 실측** (게이트웨이 강제 종료, 서버 재시작, DB 재시작, 브로커 재시작) | 지금 실측은 회선 단절 하나다. 나머지는 단위 테스트로만 확인했다. 장애별 "유실 0" 표를 채우면 설득력이 크다 | 1~2h |
